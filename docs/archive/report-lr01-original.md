## 2. Змінений маршрут

Маршрут отримання підсумку за критичністю від UI до БД і назад:

1. Виклик функції `loadSeveritySummary()` у `src/SecureLab.Api/Client/app.js` (встановлює стан «Завантаження…»).
2. HTTP-запит: `fetch("GET /api/incidents/severity-summary")`.
3. Маршрутизація в `src/SecureLab.Api/Presentation/Endpoints/IncidentEndpoints.cs` передає керування обробнику `GetSeveritySummaryAsync`.
4. Виклик бізнес-логіки в `src/SecureLab.Api/Application/Incidents/IncidentQueries.cs`.
5. Звернення до PostgreSQL через Entity Framework (`dbContext.Incidents.AsNoTracking().GroupBy(...)`), яке транслюється в SQL-запит із `GROUP BY i.severity`.
6. Формування відповіді за контрактом `IncidentSeveritySummaryResponse` (DTO) із застосуванням політики «повного переліку рівнів» і сортуванням від Critical до Low.
7. Серіалізація в JSON і повернення HTTP 200.
8. Обробка відповіді в `app.js`: безпечне створення елементів списку (`document.createElement`) та присвоєння тексту через `textContent`.

## 3. Виконані зміни

- **DTO:** Створено контракт `IncidentSeveritySummaryResponse` (severity, count), щоб не розкривати внутрішні поля `Incident`.
- **Query:** Реалізовано метод підрахунку через `GroupBy`. Застосовано політику «повного переліку рівнів» (відсутні групи заповнюються `count: 0` за допомогою `Enum.GetValues`).
- **Сортування:** Реалізовано сталий порядок виводу критичності за спаданням (Critical → High → Medium → Low).
- **Журналювання:** Додано структурований лог `logger.LogInformation` із фіксацією кількості груп без чутливих даних.
- **Frontend:** Додано обробку станів «Завантаження…», «Даних немає» та безпечне виведення помилки. Вивід даних відбувається строго через безпечні DOM API (захист від XSS).
- **Стилі:** Додано кольорову індикацію критичності через CSS (`severity-*`).
- **Тести:** Додано інтеграційний тест `GetSeveritySummary_ReturnsOrderedListWithZeroGroups`, який перевіряє контракт, порядок і політику нульових груп. Усі тести (`5/5`) успішно пройдено.

## 5. Security-сценарій

Для лабораторної роботи № 1 не застосовується (варіант 2-A не містить навмисно вразливого стану). Перед комітом перевірено `git diff --staged` — секрети (локальний `appsettings`, `.env`, токени) у контроль версій не потрапили. Безпека DOM на фронтенді гарантована використанням `textContent`.

## 6. Висновок

Під час виконання лабораторної роботи №1 розгорнуто локальний стек застосунку та прослідковано повний цикл обробки HTTP-запиту. Успішно реалізовано нову кінцеву точку `severity-summary` на рівні «добре»: додано DTO для ізоляції сутностей бази даних, реалізовано агрегацію даних на стороні БД (`GROUP BY`), враховано відсутні групи та додано структуроване логування. Клієнтська частина безпечно відображає дані та обробляє мережеві затримки/помилки, а написаний інтеграційний тест автоматизує перевірку створеного контракту.
