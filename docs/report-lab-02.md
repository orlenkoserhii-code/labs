# Звіт до лабораторної роботи № 2

## Валідація API та усунення SQL injection

**Статус:** оформлено за кодом тега `v0.2.0`, історією Git і попереднім генератором звіту 20.10.2026. Методичку ЛР 02 не надано, тому повну відповідність її формі не підтверджено. Нові runtime-перевірки не виконувалися; результати зі старого генератора позначені як історичні.

## 2. Контракт створення інциденту

`POST /api/incidents` приймає окремий `CreateIncidentRequest`: `title`, `description`, `severity`, `occurredAtUtc`. Сервер перевіряє DTO до створення entity.

| Поле / правило  | Реалізація в перевіреному коді                                                                                                                                             |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| title           | Обов'язкове, не лише пробіли; до 160 символів до Trim; зберігається після Trim                                                                                             |
| description     | Обов'язкове; до 4000 символів до Trim                                                                                                                                      |
| High / Critical | description має щонайменше 40 символів після Trim                                                                                                                          |
| severity        | Enum.TryParse + Enum.IsDefined; невідоме значення та `7` відхиляються. Ця пара сама по собі не доводить відмову для всіх числових рядків, що відповідають визначеному enum |
| occurredAtUtc   | Обов'язковий DateTimeOffset; не далі ніж на 5 хвилин у майбутньому; збереження у UTC                                                                                       |
| Службові поля   | id, ownerUserId, status і службовий час не входять до request DTO                                                                                                          |
| Owner у ЛР 2    | Серверне навчальне значення Alice; перехід на verified principal виконано в ЛР 3                                                                                           |
| Дублікат title  | 409 для інциденту, який не Closed; порівняння чутливе до регістру                                                                                                          |
| Успіх           | 201, Location і вузький response DTO: id, title, severity, status, createdAtUtc                                                                                            |
| Помилки         | 400 Validation Problem Details; предметний конфлікт - 409 Problem Details                                                                                                  |

## 3. Finding: «до → причина → виправлення → після»

**Контекст:** локальна навчальна БД, синтетичні записи, пошук у title/description через `GET /api/incidents/search`.

**Гіпотеза:** введений користувачем текст змінює структуру SQL та розширює вибірку замість пошуку літерального рядка.

**Стан до:** окремий vulnerable commit наведено в розділі 1. Попередній генератор звіту описує порівняння звичайного вводу без збігів і контрольного вводу з умовою OR TRUE: перший давав порожню вибірку, другий - п'ять seed-записів. Первинні HTTP-докази `search-before.txt` у перевірених файлах не знайдені; нове відтворення тут не виконувалося.

**Першопричина:** включення зовнішнього значення до структури SQL без параметризації. Недолік полягає в способі побудови запиту, а не в самому існуванні query-параметра.

**Виправлення:** LINQ/EF Core та `EF.Functions.ILike` з параметризованим pattern; екранування `%`, `_` і `\` для літерального пошуку; allowlist `sortBy` (`createdAtUtc`, `severity`, `status`), сталі бізнес-ранги, додатковий ключ Id і `Take(50)` після сортування.

**Стан після:** реалізацію та regression tests підтверджено за кодом. Попередній генератор описує 200 з порожнім масивом для того самого контрольного вводу і правильні збіги для USB та O'Brien. Це історичні твердження попереднього документа; первинні відповіді та повторний запуск потрібно додати.

**Позитивна регресія:** наявні тести звичайного пошуку, апострофа, літеральних метасимволів, title/description, сортування та ліміту результатів.

**Залишковий ризик:** AnyAsync перед вставленням не гарантує унікальність за конкурентних POST. Потрібний окремий захист на рівні БД або транзакції, якщо це є вимогою системи. ЛР 2 ще не надає resource authorization чи повної моделі CSRF. Висновок про всі можливі SQLi у застосунку лише з одного regression test не робиться.

## 5. Маршрути і доступ до даних

```text
HTTP POST → CreateIncidentRequest → валідація → AnyAsync → Incident → SaveChangesAsync → safe DTO
HTTP GET search → q/sortBy → allowlist / literal pattern → LINQ/ILike → sort → Take(50) → JSON
```

Відповідальні файли: `Scaffolding/Lab02Endpoints.cs`, `Application/Incidents/IncidentQueries.cs`, `Data/DatabaseBootstrap.cs`, `tests/SecureLab.Api.Tests/Lab02ContractTests.cs`. Seed і його розширення містять сталі навчальні значення; це не захист доступу до чужих ресурсів.

## 6. Відтворення і підсумки

Виконувати перевірку на коді `v0.2.0`. Reset - лише для власної локальної синтетичної БД.

```powershell
docker compose --env-file infra/.env.example -f infra/compose.yaml up -d --wait
dotnet build src/SecureLab.Api/SecureLab.Api.csproj --configuration Release
dotnet test tests/SecureLab.Api.Tests/SecureLab.Api.Tests.csproj --configuration Release
```

Попередній генератор містить запис «49 passed, 0 failed, 0 skipped». Під час оформлення він не відтворювався, відповідний первинний tests-summary не знайдено. Нову дату, команду та кількість тестів додати після фактичного запуску. HTTP-сценарії присутні в `tests/http/lab-02-checks.http` і `tests/http/lab-02-search.http`.
